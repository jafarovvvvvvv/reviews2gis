# reviews2gis — отзывы 2GIS: продажи (лиды) + продукт (готовые ответы клиенту)

## Что мы продаём

Не инструмент, а **снятую работу**. Формулировка оффера, из которой выведены все
клиентские тексты в проекте:

> Слежу за вашей карточкой в 2ГИС. Появился отзыв, особенно негативный —
> присылаю готовый ответ в WhatsApp в тот же день, вы вставляете.
> Раз в неделю отчёт: что изменилось и на что жалуются чаще всего.

Три правила, которые из этого следуют (нарушение — баг в текстах, а не мелочь):

1. **Мониторинг клиенту не продаётся.** У 2ГИС есть бесплатные уведомления о
   новых отзывах в Telegram и на почту для всех компаний, поэтому «вы узнаете о
   новом отзыве в тот же день» и «не пропустите ни одного отзыва» — не аргумент.
   В коде мониторинг остался и работает: он нужен нам, чтобы вовремя написать
   ответ, а не клиенту как ценность.
2. **Ценность — снятая работа.** Формулировки строятся вокруг «вам осталось
   вставить», а не «вы будете в курсе».
3. **Роста рейтинга по срокам не обещаем.** При сотнях накопленных оценок сдвиг
   на 0,3 требует сотен новых оценок. Ответы стабилизируют репутацию и снимают
   часть ущерба от негатива; приток новых оценок — отдельная работа, и сбор
   отзывов (QR/просьба после визита) мы пока не продаём. См.
   `outreach.build_steps` / `outreach.rating_note`.

## Установка и запуск

```powershell
pip install -r requirements.txt
python -m playwright install chromium   # нужен только резервному способу (браузер)

# параметры из .env (скопируйте .env.example -> .env) или через аргументы:
python main.py --city Алматы --category стоматология --count 30 --sender-name Эмиль

python main.py --firm 70000001026831262   # отладка одной карточки (+ печать сообщения)
python main.py --mode browser             # принудительно через браузер (по умолчанию auto)
python main.py --no-headless              # показать окно браузера
python lead_scoring.py                    # само-тесты логики приоритета
python outreach.py                        # само-тесты сообщений/аудита/wa.me
python leadgen.py                         # само-тесты прогона (каскад, прогресс, пакеты)
```

**Проще — из панели:** `python app.py` → вкладка «Поиск лидов» (форма, прогресс,
таблица лидов, кнопка «В мониторинг»). CLI остаётся для больших прогонов и отладки.

Имя и контакт для сообщений задаются в «Настройках» панели (поле «Подпись в
письмах лидам»); для CLI — `SENDER_NAME` / `SENDER_CONTACT` в `.env` или
аргументы `--sender-name` / `--sender-contact`. Пусто — в сообщении останется
заглушка `[Имя]`.

Результат прогона:

1. `output/2gis_<город>_<категория>_<дата>.csv` — лиды по приоритету (`utf-8-sig`
   + разделитель `;` — Excel открывает без проблем). Не найденное поле → `н/д`.
2. `output/outreach_<город>_<категория>_<дата>/` — **пакет для рассылки**:
   - `index.html` — дашборд: лиды по приоритету, тексты первого касания под
     каждый канал (кнопка «Копировать»), ссылка **WhatsApp с уже подставленным
     текстом**, ссылка на Instagram (если найден) и на разбор;
   - `audit_<id>.html` — одностраничный разбор карточки: метрики (с датой сбора
     данных), цитаты худших отзывов, динамика к прошлому замеру, два шага —
     отправляется уже директору (Ctrl+P → сохранить как PDF). Блок сравнения с
     конкурентом по умолчанию выключен (см. «Динамика и конкурент»);
   - `outreach.csv` — Название;Приоритет;Телефон;WhatsApp + по колонке на каждый
     канал касания (для учёта).

## Первое касание: тексты под каналы

Задача первого касания — **не вручить разбор, а выйти на директора**: узнать имя
и прямой контакт. Разбор отправляется потом, уже конкретному человеку, — иначе
он уходит в общий чат и там умирает.

`outreach.build_touch_messages(c, cfg)` даёт по тексту на канал
(`TOUCH_CHANNELS`):

| Канал | Когда | Чем отличается |
|---|---|---|
| `whatsapp` | холодный номер из карточки | представляемся по имени, называем город |
| `instagram` | Direct аккаунта компании | без представления (в Direct видно, кто пишет) |
| `admin` | **ответил администратор** | не просим «передайте», просим прямой контакт |

Правила текстов (проверяются самотестами `python outreach.py`):

- не начинать с «бесплатный разбор» и вообще с оффера — так читается рассылка;
- заходить через конкретное наблюдение по их карточке
  (`outreach.touch_observation`: негатив без ответа → весь долг по ответам →
  молчащая карточка; выдуманных чисел нет, поля те же, что в шапке разбора);
- заканчивать вопросом про имя и контакт директора;
- 3–4 предложения, одним сообщением, **без длинных тире** (в переписке они
  выдают копипасту);
- ни слова про мониторинг и «вы узнаете о новом отзыве».

В WhatsApp уходит вариант `whatsapp` — он же подставляется в ссылку `wa.me`
(телефон нормализуется к `wa.me/7XXXXXXXXXX`, код `8` → `7`) и в CSV.

«Боли» (`pain_bullets`, до 3 самых сильных: проигрыш конкуренту по рейтингу или
полоса 3.5–4.4 → негатив без ответа → молчащая карточка/мало отзывов) остались,
но живут теперь **только в разборе**, а не в первом касании.

> В **разборе** конкурент выбирается детерминированно из снимков БД и только при
> включённом флаге (см. «Динамика и конкурент») — по всей истории города, а не
> внутри одного прогона.

## Что говорит разбор карточки (`audit_<id>.html`)

Шагов ровно **два**, и это позиционирование, а не краткость:

1. **Закрыть накопленный негатив** — ответ владельца снимает часть ущерба и
   виден каждому, кто открывает карточку. При `DRAFT_REPLIES=1` шаг ссылается на
   готовые ответы под цитатами в этом же документе; без черновиков такого
   обещания в тексте нет (`build_steps(c, has_drafts)`).
2. **Не копить дальше** — каждый новый отзыв получает ответ, готовый текст
   приходит в WhatsApp.

Первый шаг появляется, только если негатив без ответа реально есть. Под шагами —
честная приписка про рейтинг (`rating_note`): ответы сами по себе оценку не
поднимают, а сдвинуть её при N накопленных оценках может только приток новых.
Шагов «включить мониторинг» и «запустить поток отзывов» (QR после визита)
**больше нет** — см. «Что мы продаём».

## Веб-панель мониторинга (продукт-MVP)

```powershell
python app.py        # -> http://127.0.0.1:8765
python db.py         # само-тесты хранилища (включая маршрутизацию и миграцию)
python tg.py         # само-тесты форматирования уведомлений
python fetcher.py    # само-тесты HTTP-способа (парсеры карточки/отзывов, без сети)
python monitor.py    # само-тесты разбора ссылок/отзывов, каскада и антиспама алертов
python bot.py        # само-тесты разбора команд бота
python ai_reply.py   # само-тесты AI-ответов (промпт/язык/парсинг, без сети)
python metrics.py    # само-тесты единого слоя чисел + часовой пояс (негатив/без ответа/окно/UTC+5)
python insights.py   # само-тесты аналитики (таксономия/агрегация/рендер, без сети)
python weekly_report.py  # само-тесты отчёта за неделю (периоды/темы/рендер, без сети)
python check_live.py --selftest   # логика сверки (без сети)
python check_live.py              # ЖИВАЯ сверка: 3 компании, таблица против разбора
                                  # + согласованность ВНУТРИ разбора
python leadgen.py    # само-тесты прогона лидов (каскад, прогресс, отдача пакетов)
python demo.py       # само-тесты демо-сидинга (без сети)
python app.py --demo # витрина: изолированная demo.db с готовой компанией
python backup.py --selftest   # само-тесты бэкапа
python backup.py --keep 14    # снимок monitor.db в backups/
```

Сценарий:

1. **Добавить компанию** — вставьте ссылку на карточку 2GIS
   (`https://2gis.kz/<город>/firm/<id>`, поддерживаются домены kz/ru/com/kg/uz/az/by,
   хвосты `/tab/...` не мешают). Первичная загрузка идёт в фоне (~15–30 сек):
   карточка читается, текущие отзывы запоминаются **молча** (baseline) —
   уведомления приходят только о тех, что появились после добавления.
2. **Привязать Telegram** («Настройки»): создайте бота у @BotFather, вставьте
   токен (или `TELEGRAM_BOT_TOKEN` в `.env`) и напишите боту `/start` — чат
   привяжется сам (поллинг в `bot.py`). **Первый чат становится админом.**
   Кнопка «Отправить тестовое сообщение» шлёт в админ-чаты.
3. **Фоновые проверки**: планировщик раз в минуту смотрит, у кого истёк интервал
   (настройка, по умолчанию 360 мин, минимум 30), и проверяет карточки по одной
   (под `SCRAPE_LOCK`, см. «Как читается карточка»). Новый отзыв → сообщение:
   звёзды, дата, автор, текст (до 500 символов), ссылка на карточку; негатив
   (≤3) — с готовым ответом. Режим «только негатив» — галка в настройках или
   `/mode neg`. Кому именно уйдёт сообщение, решает модерация (ниже). На странице
   компании есть «Тест в Telegram» — шлёт последний сохранённый отзыв с пометкой
   «тест».
4. **Отчёт за неделю** — кнопка на странице компании (с выбором получателей),
   кнопка «Отчёты за неделю — всем» на дашборде, `/weekly <N> [all]` в боте или
   галка «каждый понедельник строить отчёт» в настройках (`auto_report`).

### Модерация уведомлений: что уходит клиенту

Пока ответы пишутся руками, клиент не должен получить сырой текст раньше, чем его
посмотрели. Настройка **`moderation`** («Настройки» → «Что уходит клиенту только
после моего подтверждения», в боте `/mod`):

| Режим | Негатив (≤3) | Позитив и нейтраль (4–5) |
|---|---|---|
| `all` (**по умолчанию**) | сначала мне | сначала мне |
| `negative` | сначала мне | клиенту сразу |
| `off` | клиенту сразу | клиенту сразу |

Задержанное уведомление кладётся в `pending_notifications` **готовым текстом**
(AI-варианты уже сгенерированы — клиент получит ровно то, что вы одобрили) и
приходит в админ-чат с шапкой «На проверку» и кнопками «Отправить клиенту» /
«Не отправлять» (`send:<id>` / `drop:<id>`, обработка — `bot.handle_callback`).
Шапка сразу называет чат-получателя, а если чат клиента не подписан на компанию —
говорит об этом до нажатия. Решение принимается один раз: два админ-чата не
отправят клиенту одно и то же дважды (`db.decide_pending`). Если отправка
сорвалась, запись возвращается в очередь (`db.reopen_pending`).

Подтверждённое уведомление уходит **только чатам клиента** (`db.client_targets` —
подписки на компанию без админских чатов): вы его уже видели, второй раз слать
незачем. Оценки нет вовсе — считаем случай спорным и показываем вам.

### Отчёт за неделю (`weekly_report.py`) — то, что обещано клиенту

Не «мы ответили на N отзывов» (работа исполнителя клиенту неинтересна), а:

- сколько новых отзывов за 7 дней и сколько из них негативных;
- **темы жалоб с частотой** (очередь/запись/цены/персонал/лечение) — разметка
  той же моделью, что пишет черновики ответов (`ai_reply.get_ai_settings`,
  таксономия и классификатор переиспользуются из `insights.py`);
- динамика: рейтинг против снимка недельной давности (`rating_history`) и те же
  счётчики за предыдущую неделю;
- что осталось без ответа (до 10 цитат, остальное — «и ещё N»).

Строится **по накопленным данным, без похода в 2ГИС**; единственный внешний
вызов — классификация тем. Без ключа OpenAI отчёт всё равно строится, но блок
тем заменяется честной строкой, а не пустотой. Рендер — тот же генератор, что у
разбора лида (`outreach.AUDIT_CSS`), печать в PDF по Ctrl+P.

Отчёты обоих видов лежат в одной таблице `insights_reports` с колонкой `kind`
(`weekly` / `pain`); динамика «к прошлому разу» считается внутри своего вида.

**Расписание.** Отчёт уходит не «раз в N дней от последнего запуска» (так время
отправки уползало бы вперёд с каждой неделей), а в понедельник с 9 утра по
времени проекта — `db.weekly_due` / `db.last_slot` (`WEEKLY_WEEKDAY`,
`WEEKLY_HOUR`). Компания, добавленная в четверг, свой первый отчёт получит в
ближайший понедельник, а не тем же вечером за неделю, которой мы не видели.
Планировщик строит не больше одного отчёта за тик (раз в минуту) — это запросы
к OpenAI; отметка `auto_runs` ставится даже при ошибке, иначе упавшая компания
пыталась бы строить отчёт каждую минуту до конца понедельника.

**Кому уходит.** На каждой ручной отправке получатель выбирается на месте
(«только мне» / «мне и чатам компании»), у авто-рассылки — настройка
`report_to`, по умолчанию **только мне**. Один общий путь на все поверхности —
`monitor.build_and_send_report`, чтобы «только мне» из панели и из бота значило
один и тот же список чатов. Кнопка **«Отчёты за неделю — всем»** на дашборде
делает то же самое по всем рабочим карточкам: последовательно (параллельные
запросы к OpenAI ловят лимиты), упавшая компания не отменяет остальные, итог
приходит одним сообщением в админ-чат.

### Поиск лидов (`/leads`) — лидогенерация из панели

Вкладка **«Поиск лидов»**: город, категория, количество → кнопка «Найти лидов».
То же, что делал CLI `main.py`, но с формой, прогрессом и результатом в браузере.

- **Прогон в фоне** — как первичная загрузка компании. Страница обновляется сама
  (7 сек), показывает полосу прогресса и стадию («читаю карточку 7 из 30»).
  Одновременно идёт **один** прогон, и он берёт общий с мониторингом
  `monitor.SCRAPE_LOCK` — плановые проверки ждут, 2ГИС не дёргается параллельно.
- **Результат** — таблица лидов по приоритету: рейтинг/отзывы, «без ответа»,
  телефон, ссылки (2ГИС, разбор, WhatsApp с подставленным текстом, Instagram),
  тексты первого касания под все каналы с кнопкой «Копировать».
- **Пакет для рассылки** пишется в `output/` и отдаётся прямо из панели:
  `/leads/pack/<пакет>/index.html` (дашборд), `audit_<id>.html`, `outreach.csv`.
  Отдаются только эти имена и только из `output/` — путь проверяется, «`../`»
  не проходит (`leadgen.pack_file`).
- **«В мониторинг»** — одна кнопка в строке лида: компания заводится в БД и
  сразу уходит в фоновую первичную загрузку (baseline, молча). Уже добавленные
  показывают чип «в мониторинге» со ссылкой на карточку.
- **Журнал прогонов** живёт в памяти процесса (последние 20, `leadgen.RUNS`) —
  после перезапуска панели он пуст, но пакеты остаются на диске и видны в
  списке «Пакеты для рассылки».
- Количество ограничено `leadgen.MAX_COUNT` (120): ~1,5 сек на компанию.

### Как читается карточка: каскад способов

Карточку можно прочитать двумя способами, и они **взаимозаменяемы** — оба в итоге
разбирают один и тот же HTML и один и тот же JSON reviews-API общими функциями
`fetcher.parse_card_html` / `fetcher.apply_reviews`:

| Способ | Модуль | Замер на 10 карточках | Что умеет особенного |
|---|---|---|---|
| **HTTP** (основной) | `fetcher.HttpFetcher` | **10/10, ~0.9 с** | ничего лишнего не грузит |
| **браузер** (резерв) | `scraper.Scraper` | 10/10, **~8.6 с** | JS-рендер, клик «Показать телефон» |

Сам каскад (`FETCH_MODES`, `fetch_ways`, `fetcher_class`) живёт в `fetcher.py` —
им пользуются мониторинг (`monitor.py`), аналитика (`insights.py`) и
лидогенерация (`leadgen.py`). Браузерный класс подгружается **лениво**: пока
HTTP справляется, Playwright вообще не импортируется.

Порядок задаётся настройкой **`fetch_mode`** («Настройки» → «Способ чтения карточек»):

- `auto` (по умолчанию) — сначала HTTP, при отказе молча уходит в браузер;
- `http` / `browser` — принудительно один способ (отладка; в CLI — `--mode`).

Если выручил резервный способ, в лог пишется `способ «browser» выручил после
отказа «http»` — так видно, что основной путь деградировал, до того как посыпятся
алерты. `BlockedError` (капча) каскадом **не лечится** — с того же IP смысла нет,
прогон останавливается сразу.

**Поиск компаний тоже идёт по HTTP.** Страница выдачи
`2gis.kz/<slug>/search/<категория>/page/<N>` отдаётся обычным GET (HTTP 200,
~830 КБ) и содержит 13 ссылок `/firm/<id>` — их берёт регулярка
`fetcher.extract_firm_ids`. Браузер для сбора списка не нужен; в каскаде он
остаётся резервом. Прогон лидогенерации переключает способ **целиком**: если
HTTP не собрал ни одной карточки, весь прогон повторяется браузером; отдельная
нечитаемая карточка прогон не срывает — она просто пропускается.

**Почему HTTP основной.** В проде (домашний сервер) браузер регулярно падал с
`Page.goto: Timeout 60000ms exceeded` — 30 раз за сутки: Chromium не успевал
догрузить страницу (~685 КБ HTML плюс скрипты, шрифты, картинки) на слабом канале.
Это и порождало поток алертов «Парсер не справляется». Все нужные данные при этом
лежат в самом HTML (`og:title`, `og:description`, `"reviewApiKey"`, `"type":"phone"`,
ссылки на соцсети) и в публичном reviews-API. Заодно браузерный путь научили
**не грузить картинки/шрифты/видео/стили** (`BLOCKED_RESOURCE_TYPES`), а таймаут
навигации снижен с 60 до 35 с — резерв стал и быстрее, и надёжнее.

**Ключ reviews-API** живёт в общем кэше на процесс (`fetcher._KEY_CACHE`): добытый
любым из способов, он достаётся обоим. Стартовое значение — зашитый в бандл 2GIS
`DEFAULT_REVIEW_KEY`, дальше подхватывается живой со страницы; при 401/403/404
ключ обновляется и запрос повторяется.

**Прокси.** По умолчанию ходим со своего IP. Если 2GIS начнёт банить по IP —
достаточно задать `SCRAPE_PROXY` в `.env` (`http://user:pass@host:port` или
`socks5://...`), код готов, менять ничего не нужно.

### Алерты о поломке парсера

После `DEAD_THRESHOLD` (3) ошибок подряд по компании приходит **одно** сообщение
«⚠️ Не читается карточка». Пока проблема не устранена, повторов нет; при первой
успешной проверке приходит «✅ Снова читается» с указанием сработавшего способа.
Если проблемных компаний больше одной, в сообщение добавляется пометка про общий
сбой — это отличает сетевую аварию от поломки конкретной карточки. Список
«уже отправленных» алертов хранится в памяти процесса (`monitor._alerted`) —
после перезапуска панели по всё ещё сломанной компании придёт одно новое сообщение.

### AI-ответы на отзывы (ядро, этап 1 ROADMAP)

К каждому новому отзыву в Telegram-алерт добавляются **два готовых варианта
ответа** (OpenAI API, модель из `OPENAI_MODEL`, по умолчанию `gpt-5.4-mini`;
ключ — `OPENAI_API_KEY` в `.env` или в «Настройках» панели). Правила 2ГИС зашиты
в промпт: вежливо, без рекламы/конкурентов/споров, персонализация по тексту.
Отдельное требование в промпте — **разнообразие**: структура и открывающая
фраза ответа зависят от сути жалобы (оплата/цена, сроки/ожидание, качество,
грубость персонала) и не должны каждый раз начинаться с «нам жаль» или
«приносим извинения» — иначе владелец, вставляя такие ответы под отзывами
на 2ГИС один за другим, выдаёт шаблон/бота. Язык ответа = язык отзыва
(русский/казахский — детект по казахским буквам, а также по частым
казахским словам/основам без спецбукв — ловит неформальный казахский,
набранный обычной кириллицей). Варианты приходят в
`<pre>`-блоках без ярлыков «Вариант 1/2» — в Telegram это чистый копируемый
текст (тапом), без интерфейсных пометок; владелец публикует ответ в кабинете
2ГИС сам (автопубликации нет — это против правил площадки). Ярлыки «Вариант N»
и кнопка «Копировать» остаются только в панели (`/company/{cid}/reply/{id}`) —
там это внутренний инструмент, а не текст для пересылки.

- **Тон бренда и подпись** настраиваются на странице компании («Тон AI-ответов»).
- В панели у каждого отзыва ссылка **«AI-ответ →»** — страница с вариантами и
  кнопками копирования (↻ — сгенерировать ещё).
- В боте: `/reply N` — варианты ответа на последний отзыв компании №N.
- «Тест в Telegram» на странице компании тоже генерирует варианты.
- Деградация: нет ключа/ошибка API → алерт уходит как раньше, со статичным
  шаблоном; доставка уведомления никогда не блокируется генерацией.
- Себестоимость: ~600 токенов на отзыв (доли тенге).

**«Отправить неотвеченные владельцу» (кнопка на странице компании, режим
теста).** Для компаний, где есть отзывы без ответа, на `/company/{cid}`
появляется кнопка — фоном (`app._send_unanswered_task`) собирает все
неотвеченные (`db.unanswered_reviews`, лимит 50), генерирует AI-варианты
ответа для каждого и шлёт в Telegram: сначала шапка-сводка
(`tg.fmt_unanswered_batch_header`), затем по одному сообщению на отзыв
(`tg.fmt_unanswered_review` — как алерт о новом отзыве, но заголовок «Без
ответа», не «Новый отзыв»). **Получатель сейчас захардкожен** —
`monitor.TEST_OWNER_CHAT_ID` (Telegram-чат Эмиля), а не чаты компании: у
`Lead`/компании ещё нет отдельного поля «чат владельца», поэтому рассылка
идёт через `monitor.notify_owner_test`, а не через обычный
`monitor.notify_chats`/`notify_targets`. Когда появится привязка
чата-получателя к конкретному владельцу — заменить хардкод в `monitor.py`.

### Глубокий разбор болей на заказ (этап 2 ROADMAP)

Отдельный инструмент, **не** отчёт клиенту (тот — в `weekly_report.py`,
см. выше): бизнесу показывают **боли из отзывов и конкретные рекомендации**,
без воды. Пайплайн в `insights.py`:

1. **Deep-сбор** — `Scraper.fetch_reviews_deep` постранично берёт до 300 отзывов
   (reviews-API, та же сессия и ключ, что и обычная проверка).
2. **Классификация** (LLM, батчами по 25): каждому отзыву — темы-боли из
   **отраслевой таксономии** (медицина / красота / общепит / авто / универсальная,
   выбирается по категории компании), тяжесть 1–3, цитата-улика, плюс «что хвалят».
3. **Агрегация** (чистый Python, без сети — тестируемо): вес темы =
   частота × тяжесть × свежесть; тренд (растёт/затухает за окна 90/90 дней);
   метрики реакции владельца (% ответов, % ответов на негатив).
4. **Резюме + рекомендации** (LLM, «пиши как аудитор»): 3 действия на месяц с
   проверкой эффекта, рекомендация по каждой боли.
5. **Динамика** к прошлому отчёту («жалобы на X: было 5 → стало 2») — со 2-го отчёта.
6. **Рендер** HTML (печать в PDF — Ctrl+P), сохранение в `insights_reports`.

Где запускается:
- страница компании → «**Сгенерировать отчёт**» (фон ~2–4 мин), список готовых
  отчётов с «открыть» / «в Telegram»;
- дашборд → «**Сделать аудит**» по ссылке — отчёт **без постановки на мониторинг**
  (для продаж: приходит файлом в админ-чаты, копия в `output/`);
- бот: `/report N` — отчёт по компании №N приходит файлом в чат.

Отчёт уходит в Telegram через `sendDocument` (HTML-файл). Себестоимость —
~60–80 отзывов × классификация + одно резюме, единицы тенге.

### Кабинет клиента, дайджесты, лендинг (этап 6 ROADMAP, частично)

- **Кабинет клиента** — `/c/<token>`: read-only страница для клиента (рейтинг-пин,
  графики динамики, распределение оценок, последние отзывы, последний отчёт).
  Токен — HMAC от `panel_secret` + **per-company nonce** (`cabinet_nonce`),
  неугадываемый и привязан к одной компании; страница без форм/кнопок/секретов,
  доступна без логина. На странице компании — карточка «Ссылка для клиента»:
  **включить/отключить** кабинет (`cabinet_enabled`) и **«Обновить ссылку»**
  (меняет nonce — старая ссылка мгновенно перестаёт работать, остальные не задеты).
  Отчёт клиенту — `/c/<token>/report/<id>` (только своей компании).
- **Еженедельный дайджест** клиенту в Telegram (рейтинг + Δ за неделю, новые отзывы,
  негатив без ответа) и **отчёт за неделю** (`weekly_report.py`) — тумблеры
  `auto_digest` / `auto_report` в «Настройках» (`auto_runs`: дайджест — раз в
  7 дней от последнего запуска, отчёт — по понедельникам, см. `db.weekly_due`).
  Вручную — `/digest N` и `/weekly N [all]` в боте.
- **Лендинг** `brand/landing.html` (и `/lp`): герой с макетом Telegram-алерта, боли
  рынка KZ, шаги, тарифы, CTA на WhatsApp. Контакт `wa.me` — плейсхолдер, заменить
  на реальный номер.

### Надёжность и состояние (этап 4 ROADMAP)

- **Страница «Состояние»** (`/health`): статусы всех карточек, число ошибок
  подряд, лимиты, индикатор «парсер жив / под угрозой».
- **Алерт «парсер умер»:** у каждой компании счётчик ошибок подряд
  (`consecutive_errors`); при 3 подряд — один алерт админам «парсер не
  справляется» (2ГИС сменил структуру или блокирует). Успешная проверка
  сбрасывает счётчик.
- **Очередь под масштаб:** планировщик перемешивает порядок проверок (джиттер)
  и держит лимит `max_checks_per_hour` (настройка, по умолч. 40) — остаток
  переносится на следующий час, чтобы не словить бан 2ГИС при многих карточках.
- **Бэкап:** `python backup.py` — консистентный снимок через SQLite backup API
  с ротацией; в cron раз в сутки (см. [DEPLOY.md](DEPLOY.md)).

### Графики динамики и демо-режим (этап 3 ROADMAP)

- При каждой успешной проверке снимается **снимок метрик** (рейтинг, число
  отзывов, % ответов владельца) в таблицу `rating_history` — дубли подряд
  отсекаются. На странице компании, карточка «Динамика»: два SVG-графика
  (рейтинг 3,0–5,0 и число отзывов; чистый SVG, без JS-библиотек), распределение
  оценок 1–5★ по загруженному окну и текущий % ответов.
- **Стиль графиков** (`svg_line_chart`/`rating_distribution` в `app.py`) —
  градиентная заливка под линией и плавающая плашка со значением на пиковой
  точке, у распределения оценок — градиентные скруглённые столбцы с плашкой
  на самой частой оценке (referenced fintech-dashboard look, цвета — свои,
  `--green`/`--blue` из `CSS`).
- **Демо-режим** `python app.py --demo` поднимает панель на **изолированной
  `demo.db`** (реальную `monitor.db` не трогает) с готовой клиникой: 6 месяцев
  истории рейтинга 3,8→4,6, отзывы со свежим негативом, готовый отчёт болей.
  Для показа на встрече за 10 секунд, без скрапинга и без чужих данных. В шапке —
  пометка «демо-режим», фоновые задачи (скрапер/бот) отключены, демо-компания
  не скрапится (`firm_id="demo"`).
- Продающая упаковка (не код): [brand/sales-playbook.md](brand/sales-playbook.md)
  — открывашка, сценарий 15-мин демо, тарифы, шаблон КП, кейс, возражения.

### Маршрутизация: кому какое уведомление

- **Админ-чаты** (роль назначается в «Настройках», первый чат — админ
  автоматически) получают уведомления **по всем компаниям** + могут управлять
  ботом командами.
- **Обычные чаты** (например, группа клиента) получают **только компании, на
  которые подписаны**: добавьте бота в группу → отправьте там `/start` → на
  странице компании отметьте чат галочкой («Сохранить получателей»).
- Служебные сообщения (тесты из настроек) идут только в админ-чаты.

### Команды бота (из админ-чата)

`/list` — компании со статусами · `/add <ссылка>` — добавить компанию ·
`/del N` — удалить №N из списка · `/check [N]` — проверить все/одну ·
`/reply N` — AI-ответ на последний отзыв · `/weekly N [all]` — отчёт за неделю ·
`/report N` — глубокий разбор болей · `/digest N` — еженедельный дайджест ·
`/status` — состояние · `/interval <мин>` — интервал ·
`/mode all|neg` — о чём уведомлять · `/mod all|neg|off` — что показывать мне до
отправки клиенту · `/test` — тест · `/help` — подсказка.
Не-админам доступны только `/start` и `/help`.
Команды работают, пока запущена панель (`python app.py`) — поллинг живёт в ней.
Под алертом о новом отзыве — **inline-кнопки** «✍ Ещё вариант ответа» (перегенерация
AI-ответа) и «Открыть в 2ГИС»; нажатия обрабатываются как `callback_query`.

Хранилище — `monitor.db` (SQLite, в Git не попадает): `companies` (+статус
`adding/checking/ok/error`), `reviews` (дифф новых — `INSERT OR IGNORE` по
`(company_id, review_id)`), `chats` (+`is_admin`; старые БД мигрируются — все
прежние чаты становятся админами), `subscriptions` (компания→чат, каскадное
удаление), `settings` (токен, интервал, `notify_all`, оффсет getUpdates).
Статус ошибки виден в панели у компании; «новых за 7 дней» — бейдж в списке.
Страницы со статусом «загружается/проверяется» сами обновляются каждые 7 сек.

Технические заметки: uvicorn запускается через `server.serve()` внутри
Proactor-цикла (Windows) — иначе Playwright не сможет поднять браузер;
формы — urlencoded, но `request.form()` в Starlette требует `python-multipart`
(в requirements.txt); HTML рендерится f-строками без шаблонизатора.

### Безопасность

- Панель слушает **только 127.0.0.1** и дополнительно защищена middleware
  `local_guard`: запросы с чужим `Host` отбрасываются (DNS rebinding), POST с
  чужим `Origin/Referer` — 403 (CSRF с вредоносного сайта на localhost).
- **Секреты не попадают в HTML**: токен бота и ключ OpenAI в формах не
  отображаются (пустое поле = оставить прежний); хранятся в `monitor.db` и
  `.env` — оба в `.gitignore`.
- Весь пользовательский ввод в HTML/Telegram экранируется (`html.escape`,
  включая кавычки); SQL — только параметризованный.
- **Отдача файлов пакета** (`/leads/pack/...`) — по белому списку имён
  (`index.html`, `outreach.csv`, `audit_<id>.html`) и только из `output/`:
  итоговый путь проверяется на принадлежность папке, «`../`» отбрасывается
  (`leadgen.pack_file`, самотесты — в `python leadgen.py`).
- Бот: команды управления — только из админ-чатов; `/start` лишь регистрирует
  чат (он ничего не получает, пока его не подпишут в панели).
- **Вход по паролю** (этап 4): задайте `PANEL_PASSWORD` — панель потребует логин
  (сессия в подписанной cookie, HMAC, живёт 2 недели; ключ `panel_secret`
  генерируется и хранится в БД). Пусто = открыта (только для локали).
  `PANEL_HOSTS` — белый список доменов (Host-allowlist для VPS). `/healthz` —
  открытый пинг для аптайм-мониторинга. Деплой в интернет — по [DEPLOY.md](DEPLOY.md)
  (Docker + Caddy + HTTPS), **обязательно с паролем**.

### Если что-то сломалось

- **«Executable doesn't exist … ms-playwright …»** — процесс панели не видит
  браузер Playwright (наблюдалось на Windows: процессы из одних сессий терминала
  видят браузер, из других — нет, при существующем файле). Панель чинит это
  **сама, тремя слоями**: (1) при недоступном headless shell скрапер пробует
  полный Chromium (`channel="chromium"`); (2) при полном отсутствии браузера
  monitor запускает `python -m playwright install chromium` тем же
  интерпретатором/окружением и повторяет проверку (одна попытка на запуск
  приложения); (3) если не помогло — в ошибке показывается исходный путь
  Playwright для диагностики. Ручное лечение прежнее: `python -m playwright
  install chromium` + перезапуск `python app.py`.
- **Защита от потопа уведомлений:** если у компании ещё не было ни одной
  успешной проверки (например, первичная загрузка упала), первый успешный
  прогон всегда считается baseline — старые отзывы запоминаются молча,
  уведомления не шлются. «Новыми» считаются только отзывы, появившиеся после.
- **«error while attempting to bind … 10048»** больше не появляется: если порт
  8765 занят, `python app.py` говорит «панель уже запущена — откройте ссылку»
  и выходит. Перезапуск: закрыть старый процесс (Ctrl+C) и запустить снова.
- Ошибка проверки видна в панели у компании (текст из 2GIS/Playwright/Telegram
  дословно); статусы `загружается/проверяется` обновляются сами каждые 7 сек.

## Как работает парсинг (логика)

Данные берутся из HTML страниц и из внутреннего reviews-API 2GIS — обычными
HTTP-запросами (браузер в резерве, см. «каскад способов»). Так надёжнее и
быстрее, чем читать обфусцированный DOM.

1. **Поиск** → `2gis.kz/<slug>/search/<категория>/page/<N>` — со страницы берём ID
   фирм регуляркой `/firm/(\d{6,})` (13 на страницу, листаем до нужного кол-ва;
   стоп по 2 страницам без новых ID или по 30 страницам).
2. **Карточка** → `2gis.kz/<slug>/firm/<id>`:
   - название/категория — из мета-тега `og:title`; рейтинг/кол-во (запас) — из `og:description`;
   - телефон — из инлайн-JSON (`"type":"phone"`) или `tel:`-ссылки; браузерный
     резерв умеет дополнительно кликнуть «Показать телефон»;
   - сайт/соцсети — из инлайн-конфига карточки (`"type":"website"`) + ссылки instagram/wa.me/…
3. **Отзывы** → `public-api.reviews.2gis.com/3.0/branches/<id>/reviews?sort_by=date_edited`
   (у браузерного способа — через `page.context.request`, та же сессия/cookies/UA/IP,
   что и навигация). Из ответа: рейтинг филиала, кол-во отзывов, и по каждому отзыву —
   оценка, дата, текст, официальный ответ владельца. Отсюда считаем свежесть,
   «владелец отвечает», «негатив без ответа в топ-5», а для аудита/сообщений —
   кол-во без ответа, негатив без ответа, отзывов за 30 дней, дату последнего
   отзыва и до 3 цитат худших отзывов (оценка ≤3, текст до 220 символов).
   Дополнительных запросов пакет рассылки не делает — всё из тех же ≤50 отзывов.

### Откуда берётся ключ reviews-API (3 слоя защиты)

Ключ к reviews-API не захардкожен, а извлекается из инлайн-конфига **каждой**
карточки: `"reviewApiKey":"<uuid>"`. 2GIS может его ротировать — поэтому:

1. **Основной** — регуляркой из HTML открытой карточки (источник истины).
2. **Фолбэк при сбое API** — открываем вкладку отзывов фирмы: она сама дёргает
   reviews-API, и актуальный ключ ловится из живого трафика + конфига.
3. **Последний фолбэк** — зашитый `DEFAULT_REVIEW_KEY` (публичный ключ 2GIS) на
   случай, если формат конфига изменится.

## Откуда берутся числа (единый слой)

Таблица лидов и разбор (аудит) по одной компании обязаны показывать **одни и те
же числа**. Раньше не показывали: каждый потребитель считал по-своему, и
определения «негатив»/«без ответа» были продублированы в четырёх модулях.

Теперь все счётчики считает `metrics.py`, и только он:

| Понятие | Определение | Где задано |
|---|---|---|
| `negative` | оценка **≤ 3** | `metrics.NEGATIVE_MAX` |
| `unanswered` | нет `official_answer` | `metrics.is_unanswered` |
| окно счётчиков | **50 новейших отзывов** — одно на все счётчики; задаётся в `.env` (`REVIEW_WINDOW`) | `metrics.WINDOW` |
| «свежий» отзыв | за последние **30 дней** | `metrics.FRESH_DAYS` |
| «топ-5» | 5 новейших — окно флага «негатив без ответа» | `metrics.TOP_N` |

Окно подписывается прямо в разборе («без ответа · последние 50 отзывов») — это
и есть ответ на вопрос «из скольких». Потребители берут числа функцией
`metrics.company_numbers(c)`; в шаблоне разбора **не считается ничего**.

### «Без ответа»: одно число, три подписи

Одно и то же число «без ответа» раньше печаталось в шапке разбора и в тексте
из **разных полей** (19 и 14) — читалось как расхождение. Теперь число одно —
`unanswered_count`, — а всё остальное названо своими словами:

| Поле | Что это | Как выглядит в документе |
|---|---|---|
| `unanswered_count` | отзывов без ответа в окне | «**26** без ответа» (шапка и текст — одно число) |
| `negative_unanswered` | из них негативных (≤3) | «4 из них — негативные» |
| `unanswered_fresh` | из них за последние 30 дней | «3 — за последние 30 дней» |
| `response_rate` | доля отзывов в окне **с** ответом (обратное `unanswered_count`) | «владелец отвечает на 80%» — в причине приоритета, см. ниже |

Подпись собирает `metrics.unanswered_note` — число называется явно в начале
фразы, чтобы «из них» не путалось с другим числом рядом:
«26 без ответа из последних 50 отзывов, 4 из них — негативные, 3 — за
последние 30 дней. Всего у компании 117 отзывов.» Выводить два разных числа
под одной подписью нельзя; за этим следит приёмочная проверка (см. ниже).

`response_rate` считается один раз, в `metrics.review_stats` (окно пустое —
`None`, а не `0`: это разные факты), и течёт дальше готовым через
`company_numbers` — в снимки, в CSV (колонка «Владелец отвечает, %») и в
причину приоритета. Нигде по пути он не пересчитывается.

### Цитаты в разборе: только негатив без ответа

Блок «Что видят клиенты» показывает **только** отзывы, у которых оценка ≤3
**и** нет `official_answer`, свежие сверху, не больше трёх. Отбор делает
`metrics.review_stats` (поле `negative_quotes`), а не шаблон:

- отвеченный негатив сюда не попадает **по построению** — метки «есть ответ
  владельца» в блоке больше нет;
- цитат меньше трёх — показываем сколько есть;
- цитат ноль — **блок не рендерится**, и шаг «закрыть накопленный негатив»
  из списка шагов тоже убирается (`outreach.build_steps`). Иначе документ
  противоречил сам себе: призывал ответить на негатив и тут же показывал
  отзывы с ответом владельца.

### Черновики ответов под цитатами (`DRAFT_REPLIES`)

Готовый ответ под конкретной цитатой — единственное место, где директор видит
нашу работу, а не обещание. При `DRAFT_REPLIES=1` под **первыми двумя** цитатами
блока «Что видят клиенты» появляется готовый текст: **«Как бы ответили мы:»** +
курсивом одна строка, почему такой ответ работает. Под третьей цитатой (если она
есть) — «Остальные N отзывов без ответа разбираем в рамках пилота»: N берётся из
`negative_unanswered` (реальное число за окно, а не длина списка цитат — она
ограничена тремя).

- **Включено по умолчанию** (`DRAFT_REPLIES=1`), потому что на них опирается
  первый шаг разбора: без черновиков `build_steps` не обещает «готовые ответы
  выше». Цена — до 2 запросов к OpenAI на карточку, поэтому на больших прогонах
  лидогенерации ставьте `DRAFT_REPLIES=0`.
- **Выключено или нет ключа** — документ рендерится ровно так же, как без этой
  фичи, вплоть до байта: CSS блока черновиков (`outreach._DRAFT_CSS`)
  подключается отдельным `<style>` и только когда черновик реально есть, иначе
  он тоже не попадает в файл.
- **Генерация** — `ai_reply.draft_audit_replies` → `ai_reply._chat_completion`,
  тот же HTTP-клиент к OpenAI, что и черновики ответов в панели; своего
  клиента и провайдера фича не заводит.
- **Сбой — тихая деградация.** Нет ключа, таймаут, ошибка API — разбор всё
  равно строится, просто без черновиков; ошибка пишется в лог как `[warn]`,
  в духе `leadgen.push_to_crm`. Один сбойный черновик не гасит второй —
  у каждой цитаты свой `try/except`.
- **Медицинское ограничение.** Клиенты сервиса — медицинские клиники, поэтому
  каждая цитата сначала классифицируется той же моделью (поле `claim_type`,
  сохраняется рядом с черновиком и виден в вызывающем коде):
  - `service` (очередь, запись, регистратура, цены, график) — отвечаем по
    существу;
  - `treatment` (лечение, качество медпомощи, конкретный врач) — только общая
    формула: сожалеем, просим написать или позвонить напрямую, разберём
    индивидуально. Без деталей визита, без признания вины, без подтверждения
    или отрицания того, что автор отзыва — пациент клиники (врачебная тайна).
    Неизвестная/битая классификация тоже уходит в `treatment` — это более
    осторожный вариант (`ai_reply.parse_draft`).
- **Язык ответа** = язык отзыва — тот же детектор `ai_reply.detect_lang`, что
  и в панели: казахские буквы → казахский, иначе русский.

### Рейтинг и счётчики: четыре разных числа

2ГИС считает рейтинг по **подтверждённым оценкам**, которых больше, чем
текстовых отзывов. Поэтому смешивать их нельзя:

| Поле | Что это | DoctorDos (Костанай) |
|---|---|---|
| `rating` | рейтинг филиала от 2ГИС | **5,0** |
| `ratings_count` | всего оценок — база рейтинга | **1174** |
| `reviews_count` | текстовых отзывов | **778** |
| `branch_scope` + `branches_count` | по чему собраны данные | филиал, всего 2 |
| `org_rating` / `org_*` | те же числа по всей сети | 4,9 / 967 / 1452 |

Источник — инлайн-JSON карточки (`"general_rating"`, `"general_review_count"`,
`"general_review_count_with_stars"`, `"org_*"`), то есть ровно те числа, что
видит человек на странице. Из reviews-API (`meta.branch_rating`) значения
берутся, **только если карточка молчит**; там же читается флаг
`branch_rating_is_confirmed` — «на основе подтверждённых оценок».

> **Рейтинг никогда не вычисляется нами.** Средний балл по нашему окну отзывов
> у DoctorDos — 4,34 при реальных 5,0: считать его самим означало бы печатать в
> разборе число, которого нет на карточке. Запрет закреплён самотестом
> «рейтинг не пересчитан по отзывам» (`python fetcher.py`), а если у компании
> несколько филиалов, разбор прямо пишет: «данные по одному филиалу из 2».

### Что проверяет приёмка (`check_live.py`)

1. **Таблица против разбора** — числа берутся из отрендеренного HTML, а не из
   объекта: если шаблон снова что-то посчитает сам, проверка упадёт.
2. **Согласованность внутри документа** — число «без ответа» в шапке обязано
   совпадать с числом в тексте; два разных числа под одной подписью валят
   проверку с текстом «одно число, поданное как два».
3. **Цитаты** — в блоке не может быть отзыва с ответом владельца; шаг
   «ответить на весь негатив» и блок цитат существуют только вместе.
4. **Детерминизм** — повторный разбор обязан быть идентичным, конкурент —
   тем же.

Каждая компания печатает оба числа и список цитат с флагом `unanswered`.

### Часовой пояс: Астана (UTC+5), а не сервер

Сервер (Docker-контейнер) живёт в UTC — `.astimezone()` без аргументов и
голый `datetime.now()` берут системное время **сервера**, а не пользователя.
Из-за этого «Разбор подготовил … Данные собраны» и «проверено: …» в панели
показывали время по Гринвичу вместо астанинского (разница — 5 часов).

Единая точка — `metrics.LOCAL_TZ` (фиксированный `UTC+5`: Казахстан с 2024
года живёт без перевода стрелок одним часовым поясом на всю страну) и три
функции поверх него:

- `metrics.to_local(dt)` — datetime (в любой зоне или наивный) → Астана;
- `metrics.fmt_local(iso, fmt=…)` — то же, сразу строкой, для всех дат в
  документах и панели (замена `.astimezone().strftime(...)`);
- `metrics.now_local()` — текущий момент по Астане, для «собрано …».

Наивные (без временнóй зоны) метки в проекте считаются UTC — так их и пишет
`db.now_iso()` для всего, что хранится без явного оффсета, — это факт про
формат хранения, а не допущение.

Отдельно: **сами отзывы 2ГИС приходят с меткой `+07:00`** (свой пояс площадки,
не пользователя) — «2026-09-01T01:30:00+07:00». Календарная дата отзыва
(«Дата последнего отзыва», даты цитат в разборе) берётся **после** перевода
в Астану (`metrics.review_stats`), иначе отзыв поздним вечером по Астане мог
показаться отзывом следующего дня.

### Свежесть данных разбора

Разбор больше не может показать данные месячной давности:

- он строится по последнему снимку компании (`lead_snapshots` в `monitor.db`);
- снимок старше `AUDIT_MAX_AGE_HOURS` (по умолчанию **24 ч**, настройка в
  `.env`) — компания **перечитывается** с 2ГИС до рендера;
- перечитать не удалось → `leadgen.StaleDataError`, и **разбор не строится
  вовсе**. Молча подставить старые числа нельзя — именно так в разбор и попали
  данные месячной давности;
- в подвале и в шапке печатается **дата сбора данных**, а не дата генерации
  файла: «данные собраны 01.09.2026, 12:36».

### Динамика и конкурент

- **Динамика** — блок «Что изменилось с прошлого замера»: рейтинг, отзывы без
  ответа, негатив без ответа, текстовые отзывы (было → стало) и дата прошлого
  замера. Предыдущего снимка нет — блока нет совсем, без заглушек и прочерков.
- **Конкурент** — блок сравнения **по умолчанию выключен** (`AUDIT_COMPETITOR=1`
  в `.env` включает): раньше он подставлял разных конкурентов от прогона к
  прогону. Включённый выбирает детерминированно: топ-1 по рейтингу среди
  последних снимков той же категории того же города, сама компания исключается,
  при равном рейтинге — больше оценок, затем меньший `firm_id`. Рейтинг
  конкурента приходит из того же слоя данных, что и остальные числа.

## Приоритизация лидов

**Базовое правило:**

- 🔥 **Высокий** = отзывов ≥30 **и** свежие **и** (рейтинг 3.5–4.4 **или** есть отзывы без ответа)
- 🟡 **Средний** = поток есть (≥30, свежие), без триггеров выше
- ⚪ **Низкий** = отзывов <30 **или** нет свежих отзывов

**Понижающее правило поверх базового.** Компания вроде DoctorDos — рейтинг
5,0 при 778 отзывах, галочка 2ГИС, номинант, онлайн-запись — базовым правилом
уходила в 🔥 Высокий только из-за 9–10 отзывов без ответа, хотя продавать там
нечего: владелец и так отвечает почти на всё. Правило это отсеивает само:

> Если `rating ≥ 4.5` **и** `response_rate ≥ 0.2` → приоритет понижается до
> 🟡 Среднего, даже если `unanswered_count` большой.

Смысл: высокий рейтинг **и** владелец реально отвечает — боли нет, лид не тот.
А высокий рейтинг при `response_rate == 0` — наоборот, хороший лид: владелец
не отвечает вообще, хотя мог бы. `response_rate = None` (окно пустое) правило
не роняет — понижение просто не применяется.

**Пороги настраиваемые** (`lead_scoring.ScoringRules`): `min_reviews` (30),
`problem_band` (3.5–4.4), `downgrade_rating_min` (4.5),
`downgrade_response_rate_min` (0.2) — значения в скобках это дефолт, он же
зашит в коде явно (не магические числа). Переопределить вручную можно тремя
способами (флаг CLI главнее .env, .env главнее панели, которая пишет в БД):

- в **веб-панели**: на странице «Поиск лидов» разворачивающийся блок
  «Фильтры приоритета» — 5 полей, пустое поле показывает дефолт как
  placeholder. Значения сохраняются в настройках (`db.set_setting`) и
  применяются ко всем прогонам панели, пока их не поменяют ещё раз;
- флагом CLI: `main.py --lead-min-reviews 20 --lead-rating-band 3.0 4.5
  --lead-downgrade-rating-min 4.8 --lead-downgrade-response-rate-min 0.3`;
- переменной окружения в `.env`: `LEAD_MIN_REVIEWS`, `LEAD_RATING_BAND_LOW` /
  `LEAD_RATING_BAND_HIGH`, `LEAD_DOWNGRADE_RATING_MIN`,
  `LEAD_DOWNGRADE_RESPONSE_RATE_MIN` — их подхватывает веб-панель при
  старте, если поля в её собственных настройках ещё пустые.

Ничего не задано → используется дефолт. Самотест (`python lead_scoring.py`)
проверяет обе ветки: без переопределения работает дефолт, с ручным
`ScoringRules`/флагом — ручные значения его перекрывают.

Решение принимает одна чистая функция `lead_scoring.decide_priority` — она же
строит **причину**, всегда с меткой приоритета впереди, чтобы её можно было
читать в отрыве от остальной строки:

| Ситуация | Причина |
|---|---|
| Рейтинг в проблемной зоне + без ответа | «Высокий: рейтинг 4,2 в проблемной зоне, 39 без ответа» |
| Высокий рейтинг, но понижен | «Средний: рейтинг 5,0, владелец отвечает на 63% — боли нет» |
| Высокий рейтинг, владелец молчит | «Высокий: рейтинг 4,9, но владелец не отвечает вообще» |

Причина видна в колонке таблицы лидов и в CSV, поэтому «почему 🔥» больше не
нужно выяснять по цифрам вручную.

Определения — из `metrics.py` (см. «Откуда берутся числа»). CSV сортируется:
приоритет, затем число отзывов; в нём же — оценки и отзывы отдельными колонками,
окно счётчиков в заголовке, доля ответов и дата сбора данных.

> **Контроль на живых данных (Костанай, 01.09.2026).** DoctorDos — рейтинг
> 5,0, без ответа 10, `response_rate` 80% → 🟡 **Средний**, «владелец отвечает
> на 80% — боли нет». Рядом на той же выборке «Aesthetic Denta» — рейтинг 5,0,
> `response_rate` **0%** → 🔥 **Высокий**, «но владелец не отвечает вообще»:
> при одинаковом рейтинге понижающее правило разводит их в разные приоритеты
> именно по тому, отвечает ли владелец на самом деле.

## Архив лидов

Таблица `lead_archive` (`firm_id`, `archived_at`, `reason`) в `monitor.db` —
компании, признанные «не тот профиль» и исключённые из активной работы.
`lead_snapshots` при архивации **не трогается** — история остаётся, лида можно
вернуть (`db.unarchive_lead`).

Функции в `db.py`: `archive_lead(conn, firm_id, reason)` (повторный вызов
обновляет причину, а не дублирует), `unarchive_lead`, `archived_firm_ids`
(множество для фильтра), `list_archived` (с именем/рейтингом из последнего
снимка — для отображения).

`leadgen.run_leads` фильтрует архивных лидов сразу после сбора — они не
попадают ни в CSV, ни в пакет рассылки, ни в пуш в CRM. В `pick_competitor`
не фильтруются: заархивированный лидер рейтинга по-прежнему годится как
эталон для сравнения в разборе.

Профиль **«тяжело продать»** (кандидат на архивацию) при ручной чистке базы:
рейтинг 4,5–5,0 независимо от `response_rate` — **если** при этом не
выполняется исключение «оставить»: отзывов ≥30 **и** есть свежие за 30 дней
**и** (есть неотвеченный негатив **или** `response_rate` <20%, тот же порог,
что `ScoringRules.downgrade_response_rate_min`). Исключение существует, чтобы не
архивировать лида с высоким рейтингом, у которого владелец на самом деле не
отвечает — там боль есть, несмотря на цифру рейтинга.

## Ограничения и риски

- **UA-детект.** На старый User-Agent 2GIS отдаёт заглушку «обновите браузер» —
  используем свежий UA (Chrome 146+) и маскировку `navigator.webdriver`.
- **Серая зона ToS.** Парсинг 2GIS против правил площадки. Для разовых аудитов
  терпимо; для постоянного потока — риск блокировок, закладывайте поломки.
- **Частота запросов.** Вызов reviews-API — отдельный паттерн, его проще
  ограничить по IP/частоте, чем обычную навигацию. Не уменьшайте паузы
  (`leadgen.PAUSE`: 0,3–0,9 с для HTTP, 1,5–4 с для браузера; между страницами
  поиска — `fetcher.SEARCH_PAUSE`), не гоните большие объёмы за один заход,
  одна вкладка на сессию.
- **Зависимость от публичного ключа.** HTTP-способ опирается на `reviewApiKey`
  из бандла 2GIS. Если ключ закроют или потребуют подписанные запросы, HTTP
  перестанет работать — тогда каскад сам уйдёт на браузер (`fetch_mode=auto`),
  ради этого резерв и сохранён. Насовсем удалять `scraper.py` нельзя.
- **Хрупкость структуры.** Селекторы/эндпоинты 2GIS могут смениться — тогда
  перепроверьте через `explore*.py` и обновите парсеры в `fetcher.py`
  (их используют оба способа) и этот README.
- **Город вне таблицы** `CITY_SLUGS` транслитерируется приблизительно — проверьте slug.
