## 2026-09-02 — Новый внешний потребитель: CRM Bedel читает fetcher.py напрямую

### Что произошло

CRM Bedel (`C:\Users\Emil\Desktop\CRM Bedel`, отдельное FastAPI-приложение для
холодных B2B-продаж) подключена к живым метрикам 2ГИС через этот проект.
У reviews2gis нет ни пакета, ни HTTP API — поэтому CRM импортирует
`fetcher.py`/`config.py` напрямую (каталог в `sys.path`, модули грузятся через
`importlib.util` под своими именами, т.к. у CRM уже есть собственный модуль
`config`) и вызывает `fetcher.HttpFetcher(cfg).parse_firm(firm_id)` — ту же
функцию, что использует собственный лидген/мониторинг этого проекта.

### На что смотреть при переделке

Это значит, что `Company` (`lead_scoring.py`), сигнатура `parse_firm`
(`fetcher.py`) и `Config`/`city_to_slug` (`config.py`) — теперь публичный
контракт для внешнего кода, не только внутренний. Переименование поля
`rating`/`ratings_count`/`reviews_count`/`unanswered_count`/`fresh_count` или
смена сигнатуры `parse_firm(firm_id)` молча ломает CRM (она не в этом
репозитории, отдельным CI её не проверить). Полный контракт и список полей —
в [CRM_INTEGRATION.md](CRM_INTEGRATION.md); там же описано известное
ограничение (несуществующий `firm_id` иногда тихо возвращает нули вместо
ошибки, если reviews-API уже закэшировало ключ с предыдущего вызова).

## 2026-07-27 — Парсер: уход с браузера на HTTP + каскад способов

### Симптом

В админ-чат Telegram потоком шли алерты «⚠️ Парсер не справляется: «…» — 3 ошибки
подряд… Последняя: карточка не прочиталась». Разные компании, пачками
(21:10, 21:23, 22:07, 22:17, 22:21, 22:41, 22:55), потом само проходило и через
время повторялось.

### Диагноз (важнее самого фикса)

Гипотеза «2ГИС сменил структуру или включил антибот» **оказалась неверной**.
Логи прода (`docker compose logs app --since 24h` на домашнем сервере) показали
настоящую причину — 30 раз за сутки:

```
[warn] не удалось открыть карточку: Page.goto: Timeout 60000ms exceeded.
```

Ни капчи, ни блокировок, ни 403. Chromium просто не успевал догрузить страницу
карточки (~685 КБ HTML плюс скрипты, шрифты, картинки) за 60 секунд на домашнем
канале. При этом браузер поднимался **248 раз за сутки** ради 10 компаний.

Усугубляла архитектура: и мета-поля карточки, и вызов reviews-API шли через
Playwright (`ctx.request`), поэтому падение браузера роняло **оба** источника
данных сразу — и срабатывало условие «ни карточка, ни отзывы не прочитались».

> **Урок на будущее: сначала логи прода, потом гипотезы.** Если бы диагноз
> приняли на веру, чинили бы антибот-обвязку — то есть делали бы браузер ещё
> тяжелее, ровно в противоположную сторону от решения.

### Замер (на чём основано решение)

10 реальных карточек из `monitor.db`, один прогон:

| Способ | Успех | Среднее | Максимум |
|---|---|---|---|
| HTTP, только reviews-API | 10/10 | 134 мс | 330 мс |
| **HTTP, страница + reviews-API** | 10/10 | **861 мс** | 1434 мс |
| Браузер (как было) | 10/10 | 8600 мс | 11787 мс |

Ключевая находка: **2ГИС отдаёт всё нужное обычным HTTP-запросом.** В сыром HTML
карточки лежат `og:title` (название, категория), `og:description` (рейтинг,
число отзывов), `"reviewApiKey"` (живой ключ API), `"type":"phone"` (телефон) и
прямые ссылки на соцсети. Отзывы отдаёт публичный reviews-API по этому ключу.
Проверено и то, что **страница поиска по категории тоже читается по HTTP**
(`/search/{категория}/page/{N}` → 13 `firm_id` со страницы) — то есть на HTTP
можно перевести и лидогенерацию.

### Что изменилось в коде

| Файл | Что стало |
|---|---|
| **`fetcher.py`** (новый) | HTTP-способ (`HttpFetcher`) + общие чистые парсеры `parse_card_html` / `apply_reviews`. Кэш живого ключа reviews-API на весь процесс. Заготовка под прокси. |
| `scraper.py` | Стал **резервом**. Разбор полей выкинут — берётся из `fetcher.py` (был дубль логики, который неизбежно бы разъехался). Перестал грузить картинки/шрифты/видео/стили (`BLOCKED_RESOURCE_TYPES`), таймаут навигации 60 → 35 с. Стал 7.4 с вместо 8.6 с. |
| `monitor.py` | Каскад способов (`FETCH_MODES`, `_FETCHERS`): HTTP → браузер, с логом «способ „browser“ выручил после отказа „http“». Переписаны алерты. |
| `insights.py` | Глубокий сбор отзывов идёт тем же каскадом (для 300 отзывов это 6 запросов — браузер там был особенно избыточен). |
| `app.py` | Настройка «Способ чтения карточек» (`fetch_mode`: `auto`/`http`/`browser`). |
| `.env.example` | `SCRAPE_PROXY` — на случай бана по IP, по умолчанию пусто. |

### Принятые решения и их причины

- **Браузер НЕ удалён.** HTTP-способ держится на публичном ключе из бандла 2ГИС.
  Если ключ закроют или потребуют подписанные запросы, `fetch_mode=auto` сам
  уйдёт на браузер. Резерв — это страховка, а не легаси; удалять `scraper.py`
  нельзя.
- **Парсеры общие для обоих способов.** Иначе при смене вёрстки 2ГИС пришлось бы
  чинить в двух местах, и способы давали бы разные цифры по одной карточке.
- **Кэш ключа общий на процесс** — ключ, добытый любым способом, достаётся обоим.
- **Прокси заложены, но выключены.** Бана по IP нет; включать заранее — лишняя
  точка отказа и деньги. Когда понадобится, достаточно строки в `.env`.
- **maxun (github.com/getmaxun/maxun) рассмотрен и отклонён.** Node + Postgres +
  Redis + MinIO, no-code рекордер под кликанье по сайтам, внутри — тот же
  Playwright, то есть та же точка отказа. Плюс лицензия **AGPLv3**, а продукт
  коммерческий. Добавил бы четыре сервиса и юридический риск, не решив проблему.

### Алерты о поломке

Было: при 3 ошибках подряд по каждой компании — своё сообщение, и так по кругу.
Стало: **одно** сообщение на инцидент, тишина до восстановления, затем
«✅ Снова читается» с указанием сработавшего способа. Если проблемных компаний
больше одной — пометка про общий сбой (отличает сетевую аварию от поломки
конкретной карточки). Список отправленных алертов — в памяти процесса
(`monitor._alerted`), после перезапуска панели по всё ещё сломанной компании
придёт одно новое сообщение.

### Проверено

- Самотесты: **173 passed** (`fetcher.py` 27, `monitor.py` 20, остальные модули
  без регрессий).
- Симуляция отказа HTTP → каскад честно уходит в браузер и дочитывает карточку.
- В проде (домашний сервер, Docker): **10/10 карточек**, все через HTTP, 1.7–4 с.
  За 10 минут после деплоя браузер не поднялся **ни разу**, таймаутов — 0,
  все компании в статусе `ok`, health 200.

### Побочный эффект деплоя

Сразу после выкатки прилетело ~39 уведомлений: компании «Azu Dental Clinic» и
«MC Dent» висели в зависшем статусе с 16 июня, и система догнала накопившиеся
отзывы (14 и 25). Это не баг — штатный догон. Если в будущем поднимаешь давно
стоявшую компанию, помни: непросмотренные отзывы уйдут в Telegram пачкой.
